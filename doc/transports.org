* Transport design

[[file:../README.org][Nostril]] | [[file:architecture.org][Architecture]] | [[file:build.org][Building and running]]

Nostril separates Nostr protocol behavior from the mechanism carrying a
message. NNG is the first transport and local integration harness. It is not a
temporary replacement that must disappear when WebSocket support arrives:
local clients and services may continue to use NNG, while remote endpoints use
WebSocket, WebRTC, or another transport required by their environment or NIP.

** Shared protocol model

Event representation and validation, JSON message envelopes, filters,
subscriptions, relay state, and NIP behavior belong above the transport layer.
They must not depend on an NNG socket type, a WebSocket connection, or GUI
state.

Transport backends carry complete Nostr messages and provide lifecycle,
ordering, send, receive, error, and close behavior. The exact Til interface is
not defined yet. Its ownership and error contracts must be documented before
it becomes a public library API.

Use the normal Nostr JSON arrays across the local boundary rather than a
special NNG-only protocol. In particular, clients send messages such as
=EVENT=, =REQ=, and =CLOSE=, while relays produce messages such as =EVENT=,
=OK=, =EOSE=, =CLOSED=, and =NOTICE=. This allows common parser, state-machine,
and conformance tests to run against every backend.

NNG pub/sub topics are a delivery mechanism, not an implementation of Nostr
filters. Nostr filter evaluation and subscription semantics remain in the
shared relay model so they behave identically over another transport.

** NIP-01 baseline

NIP-01 is mandatory for interoperable Nostr clients and relays. Its public
client-to-relay transport is a WebSocket endpoint. Clients should use one
WebSocket connection per relay for all subscriptions, and relays scope
subscription identifiers to that connection. A subscription identifier is a
non-empty string of at most 64 characters.

NNG does not make a local endpoint a NIP-01-compatible public relay. It is a
Nostril transport and conformance harness for the same messages and behavior.
The local backend must preserve a logical connection identity so subscription
replacement, =CLOSE=, relay-initiated =CLOSED=, and disconnect cleanup have the
same scope they have on a WebSocket connection.

The common model must also preserve NIP-01 filter behavior: conditions within
one filter are combined with AND, multiple filters in a =REQ= are combined
with OR, =limit= applies only to stored-event results, =limit: 0= suppresses
stored events, and =EOSE= ends the stored phase without ending the live
subscription.

** Local NNG backend

NNG supplies ZeroMQ-style messaging patterns that can exercise the model
before Nostril has a WebSocket dependency:

- =inproc://= supports deterministic communication inside one test process.
- =ipc://= supports separate local client and relay processes without an
  external network service.
- Pair or client/server-style communication can exercise bidirectional client
  commands and relay responses.
- Publisher/subscriber communication can exercise relay fan-out to multiple
  consumers.

The first tests should cover the model without transport, then NNG in-process
round trips, followed by separate-process IPC. All receive operations need
bounded waits so a failing test reports an error instead of hanging.

NNG may remain useful in deployed local compositions after remote transports
exist. Code above the backend must therefore not describe it as a mock or
assume that every connection ultimately becomes a WebSocket.

*** Current prototype

The first harness uses NNG Pair0 for one client and one relay. It exchanges one
fixed NIP-01 sequence: =REQ= with =limit:0=, =EOSE=, then =CLOSE=. The
=inproc://= test exercises both peers in one process; a second test launches
=bin/nostril-relay= and =bin/nostril-cli= over a unique =ipc://= endpoint.

Two additional in-process tests keep transport and protocol claims separate.
The =test_nng_pubsub_fanout= case in =tests.til= is only an NNG fan-out smoke
test: one publisher sends a fixed =EVENT= envelope to two subscribers. The
=test_fake_relay_lifecycle= case layers two independent Pair0 control channels
for =REQ=, =EOSE=, and =CLOSE= over a shared publisher/subscriber event channel.
That split-channel arrangement belongs to the test harness; it is not the
selected architecture for a production local backend. The fixed fixture is a
signed NIP-01 event. The lifecycle test delivers valid and invalid events and
checks that each subscriber accepts only the valid event.

This proves custom-mode loading, NNG linkage, process communication, bounded
receives, basic subscription lifecycles, NNG fan-out to two local consumers,
and rejection of unsigned, wrong-ID, and bad-signature relay events. The shared
library parses NIP-01 event objects and relay =EVENT= envelopes, including
canonical tag arrays. Live mode now evaluates subscription filters and stops
future delivery after =CLOSE=. It does not store events, support
multiple clients in the Pair0 harness, or implement a public WebSocket
relay. Pair0 and the fixed 64 KiB receive buffer are prototype constraints, not
transport-interface decisions.

** Custom Til modes

*** Local live GUI feed

=nostril-relay --live [endpoint]= listens on an NNG pair1-poly feed socket (default
=ipc://tmp/nostril-live.ipc=) and a REP publication socket at =endpoint.publish=.
=nostril-gui --relay [endpoint]= attaches its pair1 and REQ sockets to these two
addresses. The suffix is part of this local IPC/inproc contract, not a second
config knob or a mapping for arbitrary TCP/WebSocket addresses.

Publications are bare signed event JSON on REQ/REP. Replies have the NIP-01 OK
shape: =["OK",id,true,""]= or =["OK",id,false,"invalid: ..."]=. Duplicates
receive =true= with ="duplicate: already accepted"=. The request/reply protocol
routes each response only to its requesting client. Invalid input echoes a
well-formed claimed ID when available, or an empty ID when it cannot be read.
An ID in a rejection is not a verified identity.

The relay verifies every publication, including retries, and routes a new
event as =["EVENT",subscription_id,event]= to matching subscriptions. The
publishing client receives it only if it also has a matching subscription.
The relay records accepted IDs in memory and acknowledges repeats without redelivery.
Clients verify before insertion and deduplicate by event ID, including across
different JSON whitespace and signature encodings of the same signed payload.

Each GUI outbox entry retains its original signed bytes. One request is active
at a time; NNG REQ retries every 500 ms and reconnects automatically. A matching,
well-formed OK makes the entry accepted or rejected. Malformed/wrong-ID replies
leave it pending and cause resubmission of those same bytes. A rejected entry
keeps the reason; it is not automatically retried. Oversized local events are
rejected locally before submission. Clients and relay must be upgraded together:
the old bus feed is no longer the live transport protocol.

*** Live subscriptions

The pair1 connection carries =["REQ",id,filter,...]= and =["CLOSE",id]=.
IDs are scoped to an NNG connection (pipe), not shared between clients. A new
REQ with the same ID replaces that connection's old subscription. Each filter
must explicitly specify =limit:0=: there is no stored-event query or history.
The relay sends =EOSE= before enabling live delivery. An unsupported or malformed
REQ with a readable ID removes its previous subscription and sends =CLOSED=;
unreadable controls receive =NOTICE=. CLOSE removes the subscription without
a reply. Disconnect removes all subscriptions belonging to that pipe.

Supported filters are =ids=, =authors=, =kinds=, inclusive =since=/=until=,
and single-letter =#tag= lists. Values within a list are ORed, fields within
a filter are ANDed, and multiple filters are ORed. IDs, authors, =#e= and =#p=
values require full lowercase 64-character hex. Tag matching uses only the
second string of each event tag. Empty lists, duplicate fields, unknown fields,
and nonzero or missing limits are rejected instead of silently broadening a
subscription. The GUI requests kind 1 under ID =local=, restricted to its active
account and followed authors. Received events are checked against that request
locally as well; an empty follow list means self-only, not an unfiltered feed.

GUI feed I/O is nonblocking with bounded work per frame. Before EOSE, the GUI
retries its REQ once per second. A dead connection clears readiness and triggers
resubscription; queued publications start once the subscription is ready.
Closing the window attempts CLOSE and then closes the connection, which also
removes its relay state. Once CLOSE is processed, later publications are not
routed to that subscription; frames already sent before CLOSE can still arrive.

The small =lib/feed.c= adapter copies bounded NNG messages, preserves the pipe
handle for targeted replies, and frees or transfers every native message. It
is built into the same archive/shared twin as NNG to keep one socket registry
on both Til backends. Control responses are retained on send backpressure;
feed sends use bounded buffers and remain best effort for slow subscribers.

This is a project-owned local transport contract, not NIP-01 over WebSocket.
The original Pair0 CLI harness remains available without =--live=.
Publication acknowledgements mean in-memory acceptance and attempted fan-out,
not durable storage or delivery to every subscriber. Feed traffic is best effort:
disconnected subscribers can miss notes. Pending publishers retry after relay
restart, while client event-ID deduplication handles a possible repeated fan-out.

Frames retain the prototype's trailing NUL and 64 KiB bound. The live receiver
checks the returned byte count, final terminator and embedded NULs before
parsing; malformed frames are consumed and dropped. Socket I/O on the GUI is
nonblocking. Closing the GUI closes both sockets and discards pending entries.
SIGINT (Ctrl-C) or SIGTERM stops the relay's loop and closes both server sockets.

The process integration test runs the real live relay with two independent
clients, checks bidirectional signed delivery and sender echoes, rejects
unsigned/malformed/tampered publications, and uses the GUI's acceptance helper
to verify duplicate and invalid-envelope rejection. It also restarts the real
relay with an outstanding publication and verifies acceptance without resigning.
In-process tests drop a reply after acceptance, verify retries do not rebroadcast,
check simultaneous clients and queued notes, and exercise mismatched/rejected
replies. A bounded timeout owns the relay child lifetime even when a test fails.
Subscription tests cover filter combinations, connection isolation for equal
IDs, replacement, EOSE, close ordering, disconnect cleanup, and the GUI's
resubscription state machine after reconnecting.

Til's =examples/custom_modes.til= demonstrates NNG-backed sender, receiver,
publisher, and subscriber modes. A Nostril-owned =mode mode= definition can
similarly auto-import a support prelude that supplies NNG bindings and link
requirements. This is analogous to =mode gui=: application files select a
concise execution environment while ordinary library modules retain explicit
ownership boundaries.

Current custom modes support =needs_main=, =decls_only=, =auto_import=,
=is_library=, =is_pure=, =run_tests=, and =debug_prints=. They are loaded with
=--extra-modes=<file>=. They do not provide mode inheritance, arbitrary entry
signatures, or custom output generators. Those limitations are sufficient for
an NNG prelude, but the mode must not become the only way to use the protocol
library.

Nostril owns the minimal Til binding and custom-mode prelude used by the local
harness. It also owns the pinned NNG 1.11 source under =vendor/nng/= and builds
the archive and shared interpreter twin into =gen/nng/=. NNG is not treated as
part of an installed Til distribution or loaded from a separate Til checkout.
The current native build path is Linux-specific; packaging and other target
toolchains remain future decisions.

** Future backends and NIPs

The [[file:websocket.org][WebSocket client transport]] now uses the shared event validation,
deduplication IDs, publication replies, and relay control parsing. It maintains
one connection and one live kind-1 subscription for the selected relay. It sends
standard NIP-01 envelopes rather than the local NNG publication framing.
Additional relay management and other transports, such as WebRTC, should reuse
those shared semantics rather than introduce separate NIP implementations.

Transport selection may depend on the endpoint, deployment, or capabilities
required by a NIP. Unsupported combinations should fail explicitly. A NIP may
add messages and state transitions or require backend capabilities, but it
should not cause unrelated protocol logic to import a transport implementation.

Backend conformance tests should replay common message and state-machine
vectors. Backend-specific tests then cover framing, connection setup,
reconnection, security, and teardown that the common model cannot exercise.

** Specification and issue workflow

The protocol overview is available under =.inspirations/nostr/=. The canonical
NIP specifications, including [[file:../.inspirations/nips/01.md][NIP-01]], are under
=.inspirations/nips/=. Both directories are Git-ignored and disposable;
upstream remains the source of truth. Planned work derived from the NIPs should
be recorded as Nostril issues with the relevant NIP, section, and reference
commit. This keeps protocol requirements traceable without copying the NIPs
into Nostril or making either reference clone part of the build.

The NIPs repository is not an implementation checklist. Nostril should select
the NIPs appropriate to its clients and relay model, treating NIP-01 as the
baseline rather than creating work merely because another NIP exists.

Issues should distinguish shared protocol behavior, a transport-independent
capability requirement, and backend-specific work. WebSocket support therefore
does not block event, filter, subscription, relay-model, or local NNG work.
