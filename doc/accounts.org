** Create and select an account

From the repository root, after building:

#+begin_src sh
./bin/nostril-gui --create-account
cp defaults/init.til "${XDG_CONFIG_HOME:-$HOME/.config}/nostril/init.til"
#+end_src

The first command creates a fresh keypair and prints only its 64-character
lowercase public key. Edit the copied init file and use that public key. Nostril
supplies the application API; no generated binding import is needed:

#+begin_src til
mode lib

init := proc() {
    nostril_config_account("main", "<public key printed by --create-account>")
    nostril_config_select("main")
    nostril_config_relay("wss://relay.damus.io")
}
#+end_src

Register additional local accounts with distinct names and public keys. Select
the initial account in init. Click the =Account:= button in the GUI and choose
another registered account to switch immediately. The selection lasts for that
process; the next launch uses init again. Creating/registering accounts still
uses =--create-account= and init.
Names here are local aliases, not published Nostr profile metadata.
The CLI =--relay [endpoint]= overrides the configured relay for that launch.
An empty configured relay keeps the GUI local-only. =--version= bypasses init.

The host selects exactly one configuration directory: =$XDG_CONFIG_HOME/nostril=
when =XDG_CONFIG_HOME= is absolute, otherwise =$HOME/.config/nostril=. Relative
XDG roots are ignored, following Tiled. Only =init.til= in that directory is
loaded. A missing file does not trigger a fallback search; an invalid file stops
startup. There is no current-directory or legacy =~/.nostril/init.til= search.
The shell example above assumes XDG_CONFIG_HOME is unset or absolute.

Without registrations the GUI retains an explicitly labelled,
session-only ephemeral identity; it never silently selects a key from disk.
Missing, corrupt, mismatched or permissive key files for a selected account
stop startup instead of generating a replacement identity.

Switching first validates the destination key and its own follow list. A failed
switch shows an error and retains the current identity, draft, feed and transport.
A successful switch closes the previous transport session, clears the timeline
and draft, stops pending publication retries, and subscribes using the new
account's follows. Already transmitted notes may still have reached a relay;
switching cannot recall them. The configured/CLI relay endpoint stays the same.

** Follow and unfollow

In the GUI, open =Following= for the active account. Type or paste (Ctrl+V) a
64-character lowercase hex public key and click =Follow= or press Enter. Each
listed key has an =Unfollow= button. Scroll long account/follow lists with the
mouse wheel; =Back= returns to the feed. Ephemeral identities cannot save follows.

Each account owns its own =follows.json=. GUI edits persist immediately, refresh
the live subscription, and remove notes that no longer match. Other accounts'
lists are not edited. The composer is inactive while either panel is open.

The headless commands remain available, using the account selected in init:

#+begin_src sh
./bin/nostril-gui --follow <64-character-public-key>
./bin/nostril-gui --unfollow <64-character-public-key>
./bin/nostril-gui
#+end_src

These headless commands load the same init and account owner as the GUI, save
the change, print the selected account identity, and exit. They do not connect
to a relay. Changes from another process are reread on switching to the account
or on a follow edit; there is no filesystem watcher. Follow targets need only
public keys, not local account registrations or private keys. npub/NIP-05 input
remains later work.

*** Petnames: names assigned by you

In =Following=, click =Name= beside a followed key. Enter a petname and click
=Save= or press Enter. =Clear name= removes the name while keeping the follow;
=Back= leaves the editor without saving. Paste is supported with Ctrl+V.

Names use 1..64 ASCII letters, digits or underscore, following NIP-02's spelling
for petname resolution. They are case-sensitive and unique to a public key
within the active account: =alice= and =Alice= are different names. Another
account can assign its own name to the same key, or reuse =alice= for a different
person. There is no global naming authority, profile-name substitution or nested
petname-path resolution in this slice.

A locally assigned petname is the primary identity label in the feed and follow
list. Without one, the GUI shows a shortened key (=You= for the active key).
Shortened public keys remain visible alongside names. The follow-list =Key=
button, the petname editor's =Copy key= button, and clicking an author line in
the feed copy the full public key. Remote profile metadata cannot rename anyone.
Changing a petname updates existing note labels immediately without resubscribing.

Petnames are the fourth field of the account's signed NIP-02 =p= tags:

#+begin_example
["p", "<public-key>", "<relay-hint-or-empty>", "alice"]
#+end_example

They are currently saved locally. Publishing this follow list in a future sync
feature would publish the petnames too; these are not separately stored private
aliases. Rename/clear updates all tags for that followed key and preserves relay
hints, trailing tag fields, unrelated tags and event content. Unfollowing removes
the key's petname as well. An imported invalid name, a name shared by different
keys, or conflicting names for one key falls back to key-based display until
explicitly repaired; Nostril never picks an arbitrary owner of an ambiguous name.

** Following feed

The following feed requests kind-1 events from the selected account plus its
followed authors. With no follows, this is an own-posts feed. It never falls
back to an unfiltered request. The local and WebSocket consumers also apply the
filter locally, so a relay cannot inject an unfollowed author's otherwise valid
note into this feed. Each connection, account switch and follow edit requests
the latest 50 matching notes (=limit:50=), followed by live delivery. Both
receivers keep at most the newest 50 matching pre-EOSE events, then merge them
into the timeline. The history limit does not cap subsequent live delivery.
The GUI shows oldest-to-newest by =created_at=, with the lowest event ID treated
as newest on timestamp ties (the reverse of NIP-01's newest-first query order).
History/live overlap is deduplicated by verified ID. Scroll the feed with the
mouse wheel; sending or changing account/follows returns to its newest end.

History availability depends on the relay. The local relay retains only its
latest 256 verified events in memory; restarting it clears that cache. There is
no durable note database or pagination yet. The first follow storage implementation
supports up to 512 follow tags.

** Files and ownership

#+begin_example
~/.config/nostril/init.til
~/.config/nostril/accounts/<public-key>/secret.key
~/.config/nostril/accounts/<public-key>/follows.json
~/.config/nostril/accounts/<public-key>/.lock
#+end_example

With an absolute =XDG_CONFIG_HOME=, all these paths instead start at
=$XDG_CONFIG_HOME/nostril/=. This replaces the prototype's earlier =~/.nostril/=
layout; no automatic migration or legacy lookup is provided.

Init is user-authored executable Til; Nostril does not rewrite it. Account data
is application-managed. =secret.key= contains 64 lowercase hex digits and a
newline. New directories are owner-only (0700), and keys, follow files and locks
are owner-only (0600). Existing storage must be owned by the current user and
have no group/other permissions. If an existing Nostril configuration directory
was created with broader permissions, explicitly correct its mode to 0700.
The shared parent (normally =~/.config=) need not be owner-only.
The store rejects symlinks at account directory/file boundaries and nonregular
files. This implementation targets the project's existing Linux/POSIX build.

Keys are plaintext by explicit choice for this first slice; permissions do not
encrypt them. Encryption/keyring support and migration are tracked in
[[file:../issues/open/2.org][#2]]. Til still does not guarantee secure erasure of managed secret-key copies.
The native account library owns the active secret; configuration snapshots and
GUI getters expose the name/public key, not that secret.

=follows.json= is a complete signed NIP-02 kind-3 event owned by that account.
Loading checks its signature, ID, kind, author, and p-tag encodings. Adding a
follow appends it without duplicates; removing one retains unrelated tags and
existing relay hints/petnames. Edits advance the event timestamp even if the
clock has not advanced. Local changes are not automatically published to relays;
NIP-02 import/synchronization remains a separate step.

All reads/edits lock the account directory's lock file. Follow edits reread the
latest event while locked, write a new 0600 temporary file, fsync it, rename it
atomically, and fsync the directory. Concurrent writers therefore do not lose
each other's additions. Key creation is exclusive and never overwrites a key.
Errors before atomic replacement preserve the prior follow file; no read error
is treated as an empty/default list. A post-rename directory-sync error is
reported even though the complete replacement may already be visible.

** TilVm bridge, following Tiled

=lib/accounts/nostril_startup.til= is the single native owner of staged config
and the active account. The compiled GUI and guest init both use the generated
=gen/nostril_startup_api.til= binding to the same shared library instance. A
static host copy plus a separately loaded guest copy would split that state.

The generated bridge also exposes host operations =nostril_account_count()=,
=nostril_account_name_at(index)= (owned name, empty for an invalid index), and
=nostril_account_switch(root, name)= (empty on success, owned diagnostic on
failure). The native owner retains registrations and validates before replacing
active state; GUI code receives no secret keys. These are prototype APIs, not a
new NIP or a stable external ABI. =src/account_feed.til= owns the active GUI
transport handles, timeline and retry queue, with explicit open/close lifetime.

Petname edits use =nostril_account_set_petname(pubkey, name)=, returning an owned
diagnostic or empty on success. It locks and rereads the latest signed list,
checks uniqueness there, signs and atomically writes, then updates the native
owner's key-to-name cache. Failures retain the previous active cache. Getters
=nostril_account_petname= and =nostril_account_author_label= return owned strings
for the active account. The protocol layer owns validation/tag editing and can
return an owned =nostril_follows_petnames= map or a single validated petname;
=nostril_relay_event_pubkey= exposes only a verified author's key. The curated
host bindings use string results, not shared mutable maps. These remain prototype
APIs with the same shared-library ownership boundary.

=src/nostril_init.til= uses the matching installed SDK recorded by the build,
loads =mode lib= init in-process with a host prelude importing the generated API,
looks up =init()= and calls it. User helper imports resolve relative to the init
file and also receive the host API. Registration is staged;
only after success are the selected key and follow list validated and adopted.
Failures clear staged/active state and report owned diagnostics. There are no
runtime compiler subprocesses; tests run the compiled loader with an empty PATH.
The initial slice has no retained guest commands, so its VM can be destroyed
after init while the native account owner remains alive through the GUI loop.

Use only the configuration registration/select/relay operations during init.
Config is trusted code, not a sandbox: arbitrary file/native side effects from
user code are not rolled back. The loader resets its staged configuration;
it does not promise a filesystem transaction for arbitrary guest code.

As in Tiled, the host supplies the prelude's import base, keeping generated paths
out of user configuration. The development build records explicit SDK/API paths;
rebuild after moving the checkout or changing the installed Til SDK. A relocatable
Nostril runtime installer is not implemented yet.

** Verification

The canonical suite runs =test/accounts_model.til= in a compiled host with an
empty PATH. It checks implicit API access in init and relative helper modules,
shared init/host state and process identity, repeated
loads, persistent identity, per-account follow isolation, failed-init rollback,
missing/corrupt/symlink/permissive key rejection, follow signature validation,
and preservation of tag metadata. Process tests exercise headless follow edits,
concurrent writers, version bypass, filesystem modes, XDG/default selection and
absence of missing-file or legacy fallback. Network tests inject
valid but unfollowed notes and check both backends drop them locally.
The account model additionally exercises the GUI's session controller against
a local relay: successful/failed switches, old pending-queue cleanup, follow
subscription replacement, timeline pruning and per-account isolation. The X11
=test/gui_send.til= check uses real account-picker, Follow and Unfollow controls,
checks signed files for both owners, and verifies draft reset and Send/Enter.
The WebSocket fixture exercises the same controller's account switches, signed
publication under the new identity, and rejection of queued events after unfollow.
Petname coverage includes signed persistence, case-sensitive collisions, locked
file reload, failed writes, alias clearing, per-account isolation, ambiguous
import fallback and preservation of relay hints/extra fields. GUI checks exercise
Name/Save/Clear and verify immediate author-label changes using captured pixels.
